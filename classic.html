AyurIP-Sahayak

Live demo ↗ Code ↗

RAG system · Python · live

A research assistant for Ayurveda, traditional knowledge and Indian IP law. Ask in English, हिन्दी, ಕನ್ನಡ or Hinglish; it answers only from its sources and cites the exact page behind every claim.

0.99answer faithfulness0.95retrieval Hit@14 languagesEnglish, Hindi, Kannada, Hinglish

Read the full write-up architecture, method, results, what broke

How it works

  1. Retrieval written by hand. Section-aware PDF chunks, Gemini embeddings and NumPy cosine search, plus BM25 and Reciprocal Rank Fusion built from scratch to compare against.
  2. Decisions from data. Hybrid search is the usual advice. On 38 labelled questions it lowered MRR from 0.97 to 0.93, so dense search stayed the default.
  3. Answers judged, and the judge tested. A model from a different family checks every answer claim against its passages. I planted 15 false sentences to test it; it caught all 15.

Built with Python, FastAPI, Google Gemini API, NumPy, React, Docker, GitHub Actions, and pytest (47 tests).

What broke, and how I fixed it

  1. 01

    The first deploy ran out of memoryAyurIP

    A local PyTorch embedding model went past the free server's 512 MiB. I moved to an embeddings API and plain NumPy search.

    Down to 5 runtime packages
  2. 02

    The "best practice" made search worseAyurIP

    Fusing in keyword search pushed correct passages down a rank or two. Dense search stayed the default; hybrid is one setting away.

    MRR 0.97 vs 0.93
  3. 03

    Kannada answers showed broken lettersAyurIP

    The model slipped Devanagari letters into Kannada words. I mapped them across Unicode blocks (they sit 0x380 apart), with tests.

    4/15 → 0/15
  4. 04

    English questions came back in KannadaAyurIP

    A Kannada example in my own prompt pulled the model off course. The code now picks the reply language and states it in the prompt.

    15/15 correct

NestFinder

Tool-calling agent · Node.js · live

An AI flat finder for Bengaluru. Describe how you live, and an agent decides which tools to call to find flats that fit, check whether the rent is fair, and compare a shortlist.

Pick a message. Watch which tools the agent chooses, then its reply.

Recorded runs from the 20-case agent eval (2026-11-01): real messages, real tool calls, real replies, cut where the eval log cuts them.

Read the full write-up screenshot, architecture, method, results, what broke

How it works

  1. An agent loop from scratch. Five tools, streamed replies, at most three tool rounds, a repair step when the provider rejects a call, and a fallback model when the rate limit hits.
  2. The AI talks, the code decides. Match scores, fair-rent medians and distances come from rules with tests, so every number on screen has a reason.
  3. Observable and safe. Every model call is traced with OpenTelemetry in Langfuse, phone numbers masked. The agent can suggest a visit; only the user can book it.

Built with Node.js, Express.js, React, MongoDB, Groq API, Langfuse, OpenTelemetry, and node:test (26 tests).

What broke, and how I fixed it

  1. 01

    "My office is in Whitefield" got an empty replyNestFinder

    A strict enum made the provider reject the whole tool call, silently. Free-text names are now resolved in code, with a repair loop.

    18/20 → 20/20
  2. 02

    Every visitor would have shared one rate limitNestFinder

    I guessed two proxy hops; the live deploy had four. I measured the hops on production and set the proxy trust to match.

    Measured, not guessed
